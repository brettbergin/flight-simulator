## Exact pacing inputs and expected values

There are 25 schedules: five scales (1/4, 1/2, 1, 2, 4) crossed with 30, 60, 144, 240 Hz and jitter. Absolute frame timestamps are the floor of `frame_index * 1000000 / frame_rate` microseconds; each supplied interval is the difference of adjacent absolute timestamps. This avoids cumulative per-interval rounding. Jitter repeats `[1000,5000,17000,33000,50000,0]` microseconds and clips the final interval. Duplicate timestamps mean a legitimate zero elapsed interval.

Every schedule ends after exactly one second of simulation time: caller durations are 4, 2, 1, 1/2 and 1/4 wall seconds respectively. Expected completed ticks are the floor of the closed-form rational total `wall_us / 1000000 * 120 * scale`; exact remainder times 4000000 gives debt quanta. The oracle does not duplicate a mutable debit loop. Each row records elapsed input, completed ticks for that call, cumulative ticks and remainder. All end at tick120/debt0. Every actual due batch is below the overload guard.

Native fixture cuts are ticks30/60/90/120, with the first caller row reaching each cut recorded. The promoted schedules explicitly subdivide original caller intervals at these native cuts. Native command/lifecycle boundaries are therefore equal despite different caller cadence. They do not imply equal wall frames or concurrent independently polled controls. The actual driver stores the identical four pilot intents at these native boundaries, so each next due step admits commands at ticks1/31/61/91 with sequences1/2/3/4. It compares actual state/weather, delivered commands and lifecycle records at equal cuts, normalizing only fresh session IDs. Same-scale event records match exactly; across-scale checks compare state and command records because scale-event payloads legitimately differ. These JSON rows contain no invented native state or OperationalEvents.

The lifecycle example accrues 1920000 fractional quanta, excludes 10 seconds paused wall time, changes scale while paused, resumes and changes scale again only at settled boundaries. The final exact simulation time is 7.5 ticks: seven completed ticks with 2000000 quanta retained. Pause/resume/scale event contents still require actual bridge replies; their acknowledgements must never become synthesized records.

## Geometry expectations

The analytic basis uses latitude30deg and longitude60deg, so all ECEF axes contribute to the fixed East/Up/South rotation. The arbitrary canonical ECEF origin is intentionally a mathematical frame example, not a new geographic/native-world fixture. Ownship local position `[64,16,-32]` rebases by `[128,-8,40]` to `[-64,24,-72]` ideally. Canonical ownship and camera inputs remain unchanged; only origin-local positions change.

The JSON supplies binary64 inputs, then derives exact rational dot products on those actual supplied values. These are the primary expected values, rather than pretending rounded ECEF input matches the ideal radicals exactly. It also gives correctly rounded final float32 component bit patterns. A future checker should account explicitly for binary64 arithmetic roundoff before final float32 conversion; no aircraft/physics tolerance or pixel/audio budget is selected or tuned here. Origin-independent camera-minus-ownship is verified in exact rational arithmetic at both origins. Camera offsets are small body-frame values under a30deg body roll, with analytic quaternion and common-frame basis supplied.

A separate frame-change example has equal raw identity body-to-current-NED quaternions at current latitudes30 and60deg. Their converted common-anchor bases differ by30deg; the shortest-arc midpoint is an explicit15deg analytic basis. Blending the equal raw NED quaternions before frame conversion cannot yield that midpoint. This detects frame confusion without depending on the nonexistent consumer. Position interpolation remains canonical ECEF; this angular example does not claim that interpolating ECEF positions produces the midpoint geodetic latitude.

Prepared-provider hashes, raw instruments/maps/contact values and authoritative state are outside this mathematical oracle and must remain invariant in actual future adoption tests. Projection<=0.5px and relative audio<=1mm remain existing acceptance bounds, with no new or relaxed performance/fidelity claims.

## Actual consumer driver

The runner stages `app/simulation/` at `res://simulation/` and this directory at `res://sim_loop_tests/`. Load `facade_checks.gd` and call its static `run(model_root)` method. It returns active check counts/failures and actual record evidence rather than relying on assertions disabled in exports. Default facade construction uses the actual ClassDB extension. Explicit adapter fixtures supplement actual native tests for unreachable malformed/partial reply conditions and must be labeled synthetic. Origin participant checks are a separate driver owned by the origin lane.

The original private mathematical packet was authored before the consumer existed (JSON SHA336cc1d905e1b2ebbba3a7473b74e34df01bf75adb1176522bb8b75ccc1fea19). Promotion adds only declared input/lifecycle cuts and explicit float32 expectation values; no measured results or native coefficients fit these expected values.

The active scalar-double helper checks use a conservative2e-12 absolute arithmetic allowance authored before the first consumer comparison. Final float32 projection components in these fixtures are checked against the precomputed rounded values; cardinal artist axes are exact. This allowance is separate from native physics, wire codec rounding and the existing pixel/audio adoption budgets. Unreachable one-quanta/near-INT64 debt injections remain analytical reference cases; live guard cases use actual reachable wall intervals.

First consumer comparison chronology: the original JSON numeric encoding rounded several large binary64 ECEF inputs by a few ULP in Godot before cancellation; analytical expected values were unchanged.
